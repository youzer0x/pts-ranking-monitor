# PIPELINE ARCHITECTURE — Stage2 の構造削減

Claude Routine のセッション消費を抑えつつ、変動要因の裏取り品質を維持するための設計。

## 背景

2026-07 の日次実行が**利用上限に到達**して停止した。旧方式の Stage2 は
「1銘柄=1サブエージェント・タスクプロンプトに row の JSON 全体と【調査パラメータ】雛形を貼付」で、
28行の日に約19〜21のサブエージェントを起動し、起動数に上限が無かった。

隣接する `tse-ranking-monitor` は 2026-07-14/15 に同じ壁に当たり、同様の構造削減で回復して
以後 30行/日を上限到達なしで回している。本設計はその実証済みの方式を PTS へ移植したもの。

## 決定事項

1. **1銘柄1エージェントと row 全文の貼付を廃止**し、決定的な前処理で最大5銘柄
   （高リスク・深掘りは3銘柄）のコンパクトなバッチを作る。
2. **親が渡すのは `batch_id` と `batch_path` だけ**とし、row・plan・長文仕様を貼り付けない。
   サブエージェントは自分でバッチファイルを読む。
3. **LLM に渡す前に機械的に圧縮する**。材料窓の外のニュース・TDnet と重複する株探見出し・
   古い継続テーマ見出し（`prior` は2件まで）・`dropped_turnover`/`dropped_mcap` を落とす。
4. **株探ニュースを Stage1 で事前取得する**。実測で `disclosures` が空の行は約69%あり、
   その全部がサブエージェント側の WebFetch を要していた。Python 側の1回に寄せる。
5. **掲載上限を20行にする**。実測（公開済み32営業日・387行）で中央値9.5行と通常日は発動しないが、
   **最大は67行（2026-07-30）**に達する。20行超は3日（07-09の28行・07-28の23行・07-30の67行）で、
   落ちる行は通算58行＝15.0%（うち47行は67行の日1日分）。
   67行を旧方式で回せば単純計算で45以上のサブエージェント起動となり、上限到達は避けられない。
   上限値の再検討余地はあるが、**青天井のまま運用しない**ことが要件。
6. **ディスパッチ予算を機械的に強制する**。`reserve_dispatch.py` がミューテックス下で台帳を
   加算し、枯渇したら委譲できない。モデルの判断と無関係に総起動数が頭打ちになる。
7. **モデルは変更しない**。親ルーチンと調査エージェントは Sonnet・effort=max を維持する。
   モデル変更は構造削減の実測後に別途 A/B 評価する。

## 予算値

```
INITIAL_DISPATCH_LIMIT   = 8    初回 pending の上限。超過は planner か ranking の異常とみなし exit 2
TOTAL_DISPATCH_LIMIT     = 12   再試行を含む総起動数の絶対上限
PER_BATCH_DISPATCH_LIMIT = 3    同一バッチの再試行上限
```

掲載上限20行・委譲対象が約7割・1バッチ3〜5銘柄という前提から、東証版
（30行→initial 12、total/initial=1.5）を20行にスケールした値。

## 受入基準

- 初期 pending ≤ **8**、総予約 ≤ **12**
- 旧方式の静的 LLM 入力文字数に対して **70% 以上削減**
- 空 factor **0**、`compile_research_results.py` の MISSING **0**
- `factor_kind` の分布と出典の質が旧方式と遜色ないこと（開示／報道／テーマ）
- **運用10営業日で利用上限到達 0**

## 実測（移植時点）

`docs/data/2026-07-09.json`（28行・利用上限で落ちた日）を planner に通した結果：

| 条件 | サブエージェント起動数 | inline | 委譲 | バッチ入力合計 |
|---|---|---|---|---|
| **旧方式**（1銘柄1タスク） | **約19〜21** | 5〜7 | 21〜23 | row JSON をタスク本文に貼付 |
| 28行そのまま・ニュース無し | 8 | 5 | 23 | 9,020 B |
| 20行上限・ニュース無し | 6 | 3 | 17 | 6,820 B |
| **20行上限＋`kabutan_news`** | **4** | 3 | 17 | 8,538 B |

最下段が実運用に相当する（`build_ranking.py` が株探ニュースを事前充填するため）。
`deep` ルート（3銘柄バッチ）だった行が `news` ルート（5銘柄バッチ）に移り、**起動数は 4** になる。
**旧方式比で約 1/5。** 総予約は 4 で上限 12 に対して十分な余裕がある。

バッチ入力バイト数は 6,820→8,538 と増えるが、これは株探見出しを**同梱した**分であり、
その代わりにサブエージェント側の株探ページ WebFetch（従来は委譲行の約69%で必須）が消える。
取得済み HTML 本文がサブエージェントのコンテキストに積み上がるコストの方が桁違いに大きいため、
差し引きでは削減になる。

再現手順は `tests/test_stage2_integration.py`（plan → reserve → compile → merge_factors を
オフラインで通し、空 factor 0 と予算内完了を検証する）。

- クラスタ正規化（PTS は `factor_kind` の40%が「テーマ」なので効果は見込める）
